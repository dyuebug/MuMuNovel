## 3. Binary Identity 与 PID 安全合同

### 3.1 启动证据

启动步骤新增以下证据：

- `rust-backend-binary-path.txt`：`realpath` 后的绝对路径；
- `rust-backend-binary-sha256.txt`：构建产物 SHA-256；
- `rust-backend.pid`：真实 server PID；
- `rust-backend-identity.json`：期望/观察路径、期望/观察 SHA-256、PID 和身份状态。

server 启动后立即读取 `/proc/<pid>/exe`。路径或 SHA-256 任一不一致，workflow 失败关闭，不进入
readiness 和 Playwright。

### 3.2 cleanup 前复核

cleanup 不再把 PID 文件视为充分授权。发送信号前必须再次验证：

1. PID 是非空纯数字；
2. 期望 binary 路径和 SHA-256 文件存在；
3. PID 仍存在；
4. `/proc/<pid>/exe` 可读取；
5. 实际路径和 SHA-256 与启动证据一致。

任一身份条件失败，写入 `cleanup_status=signal_refused` 并返回非零；不得对该 PID 发送 `TERM`
或 `KILL`。这避免 GitHub Runner 上 PID 重用导致误杀未知进程。

## 4. Artifact 合同

统一的 `e2e-diagnostics` 现在可包含：

- migration stdout、stderr、退出码；
- release preflight stdout、stderr、退出码；
- `/readyz`、`/releasez` 响应和 HTTP 状态；
- Rust backend 日志、PID、binary 路径/SHA-256、identity JSON；
- Playwright 完整日志和原始退出码；
- lifecycle JSON；
- `runner-success.json` 或 `runner-failure.json`。

`rust-readiness-diagnostics` 使用 `if: always()`，成功与失败路径都会上传。成功 manifest 只在
cleanup 成功后生成，并绑定 binary 路径/SHA-256、run ID、attempt，以及两个不同语义的提交字段：

- `github_sha=${GITHUB_SHA}`：Actions 实际执行 SHA；PR 事件中通常是 synthetic merge SHA；
- `github_head_sha=${GITHUB_HEAD_SHA}`：候选分支 SHA；PR 使用 `pull_request.head.sha`，push 回退到 `github.sha`。

失败路径也必须写入同样的两个 SHA 字段。不能把 PR merge SHA 误标为候选 head SHA。Playwright HTML
report 继续仅在失败时上传。
